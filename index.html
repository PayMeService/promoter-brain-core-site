01The system in one picture+

Four packages in one workspace, one Python environment, one lock file. Two of them are engines a person uses; two are the ground they stand on.

ground

contracts

Pure shared definitions: names, shapes, compatibility rules. No database, no network, no secrets. Everything imports it; it imports nothing of ours.

ground

data-transfer

The one place that opens a session to the company database, read-only, and knows how to copy, check, seal and swap a snapshot. It also holds the one write-scoped publish session (chapter 7).

engine

profiling

Reads websites, asks an AI a fixed set of questions per lens, stores the answers in tables named after the person and their selection.

engine

serving

Builds audience lists for a seller from the buyer data and the profiling answers, with a browser studio to run and inspect them.

contracts  ←  data-transfer  ←  { profiling, serving }

The arrow is the whole architecture: dependencies point one way. The engines share contracts and transfer mechanics, never runtime modules and never a writable table. They never import each other. A check runs on every change to keep the arrow pointing that way.

Each engine is a website on your own machine: the profiling app on port 8010, the serving studio on 8020. Everything they read and write lives in one local PostgreSQL container; serving adds a small Neo4j graph for the evidence behind a list.

02Who owns what+

Every store has exactly one writer. That single rule is what makes rollback, promotion and the hand-off safe: nobody ever writes into a table somebody else is swapping.

Contracts own no store at all. Data-transfer writes local data only through three named modules and only over loopback. Setup writes settings files and starts containers, nothing in a database.

03Three phases and what never happens+

Setting up, moving data, and operating are separate phases. Nothing slides from one into the next on its own; each is started by a person, on purpose.

1 · setup

Provisions, only

The uv preflight, host checks, the shared environment, the two settings files, the resource profile, the containers with health checks, and a record of what is installed.

Never: a copy from the company database, a job, an outside call, a refresh or rollback, an engine process, or a deletion of settings, volumes or data.

2 · data

Explicit, read-only at the source

A person types data bootstrap, refresh or rollback. Only these commands open a session to the company database, and that session can only read.

Never: a user workload, scoring, export or evidence publication.

3 · operate

Local data, explicit external calls

The apps, profiling jobs and serving runs use local stores. Profiling can also call website extraction and Gemini APIs. The studio's refresh and rollback buttons start a phase-2 operation, on purpose, with the same read-only session the command line uses.

Never: company-database access outside a started data operation or the person's hand-off answer.

4 · hand-off

The one write

After a run, on the person's click, the result tables are published into one schema of the company database through a separate, write-scoped session. Chapter 7.

04The data ladder: how a copy becomes the live copy+

Both engines move data the same way, rung by rung. Copy or gate failures leave the active copy untouched. After a committed promotion, interrupted file finalization is healed from the authoritative database stamp.

  1. Preflight. Read the company database's catalog only: are the expected tables and columns there, with the expected types; is there room on the local volume (2.2 times the source estimate). Copies nothing; every issue is one line naming the table or column.
  2. Snapshot. Open one consistent view of the source so a long copy never sees half an update. While tables stream, the session that holds the snapshot is kept alive every 30 seconds.
  3. Stage. Copy the tables into the staging schema, in chunks, with progress rows in the engine's state schema so an interrupted copy is visible.
  4. Verify. Row tallies and shape checks on the staged copy.
  5. Prepare or derive. Profiling builds its indexes and statistics. Serving runs its gates (tallies, a census, the profiles source) and derives the label surfaces from the person's profiling answers.
  6. Manifest. A sealed, digested receipt of what was copied and how it was derived. Nothing becomes visible before the manifest exists.
  7. Promote. One atomic swap: staging becomes active, the old active becomes previous, the old previous is dropped. A reader holding the tables makes the swap wait, then refuse, never corrupt.
  8. Stamp. The database stamp is the authority; filesystem pointers heal from it.
Rollback swaps active and previous: local, atomic, no remote access. Doing it twice rolls forward again. Each engine keeps exactly one previous vintage. Two advisory locks guard all of this: an engine mutex, so two data operations cannot overlap, and a swap key held shared by readers and exclusive by promote and rollback.
05Inside the profiling engine+

Its source is the website list copied by the ladder. A job takes a selection of websites and a lens (purchase drivers, political, or psychological: the set of questions the AI is asked), streams the pages, asks, and writes one row per website.

Answers land in a workspace: the person's name plus an optional selection tag. Each workspace has its own result table per lens, profiling.<person>_<tag>_<lens>_websites, and its own registry of labels. Two jobs with the same workspace and lens append to the same table; a new tag re-profiles addresses another tag already covered. The name bound (12 characters) and the tag bound (22) are chosen so every allowed table name fits PostgreSQL's identifier limit exactly.

The worker holds the shared swap lock while streaming its source workload. Once the workload is frozen in memory, model analysis releases that source-table lock. The app's storage module is the only writer of the result and registry schemas.

06Inside the serving engine+

Its vintage is the buyer data plus one profiles table: the person's published purchase-drivers answers. The data commands resolve which table that is, in a fixed order: an explicit pin in the settings, else the person's own published table, else a documented fallback. An absent explicit pin does not fall through. The choice is printed as a report-only gate and recorded in the manifest, so every vintage says where its labels came from.

From that table the engine derives two surfaces during the ladder's derive rung: a label cell per website (the analyst's flattening of the answer JSON at a fixed score and confidence bar) and a seller write-up. A run then builds an audience list for a seller against the active vintage, breaking ties with the person's tie salt so the same input always gives the same list, and can keep the evidence behind it and publish that evidence to the local graph on request.

Runs hold the runtime reader lock; a refresh or rollback that needs the exclusive swap key waits for them, then refuses rather than swapping under a run.

07The hand-off loop+

The only write this system ever makes to the company database. When a profiling job finishes, its page asks: copy these result tables now, or later?

  • Copy now first checks reachability within five seconds, then, in a separate transaction for each table: create profiling.<table> if absent with the local table's exact columns, copy the rows into a temporary table, insert the new ones (ON CONFLICT DO NOTHING). Repeating the same rows inserts zero rows; later additions to the workspace can still be published. Multi-table publication is not one all-or-nothing transaction.
  • Later runs the same check and records a milestone; the banner and the Hand-offs panel show it until the person acts. Nothing is scheduled, nothing retries on a timer, nothing runs at start-up or from setup.

The session uses separate credentials with privileges to create and fill tables in the profiling schema and to create temporary tables. Its statement allowlist is pinned by value: it can issue nothing else, no drop, delete, update, alter or grant. The loop closes when the serving data commands resolve that published table as their profiles source (chapter 6): websites in, answers published, audience lists built from the person's own answers.

Milestones outlive the process: a copy that was mid-flight when the app stopped comes back as failed and retryable; a postponed one stays listed even after the job's page is gone, because the tables are still local.
08Local infrastructure and settings+

One PostgreSQL container serves both engines with two least-privilege roles and engine-prefixed schemas, bound to the machine itself only. Serving adds Neo4j. Committed Compose files carry portable defaults; setup measures the machine (CPU, memory, disk, free ports), picks a resource profile, computes one host-wide budget for the installed scopes, and writes it to an ignored infra/resources.env. A busy default port gets an override there, never an edit to the committed defaults.

Each engine keeps its settings in one file only the person can read. The keys, never the values:

KeyRole in the logic
PROMOTER_BRAIN_USER_NAMEthe person: names every result table, the workspace, the branch, and the profiles table serving looks for; the same value in both files
GEMINI_API_KEYthe AI the profiling worker asks
*_SOURCE_PG_*the read-only session the data ladder opens; optional until the first copy
PROFILING_PUBLISH_PG_*the write-scoped hand-off session; optional, most people leave it for later
SERVING_PROFILING_TABLE, SERVING_PROFILING_SELECTIONthe explicit pin and the selection tag in the profiles-source order
SERVING_TIE_SALTthe tie-breaker that makes lists repeatable
PROFILING_API_PORT, SERVING_STUDIO_PORTwhere the two apps listen
09Install and run+

The repository is private; a team member gives your GitHub account read access. On Ubuntu 22.04 or newer (or WSL), once: sudo apt install gh, then gh auth login. Then one line:

gh repo clone PayMeService/promoter-brain-core ~/promoter-brain-core && ~/promoter-brain-core/install.sh

A guided screen asks which engine (or "not sure"), your settings in plain language, reads your GitHub account, makes a branch named after you, runs setup with a progress bar, writes your notes into the README and the rules, and offers, never forces, the data copy. Re-running it is safe.

The commands you will use

uv run promoter-brain-profiling api serve
uv run promoter-brain-serving studio serve
uv run promoter-brain-<engine> data preflight

Rung one of the ladder, alone: look, copy nothing.

uv run promoter-brain-<engine> data bootstrap

The first copy, the whole ladder. refresh later, rollback to go back one vintage, status to see where you stand.

~/promoter-brain-core/install.sh --check

What is installed here, and is it healthy.

When something goes wrong, every message ends with what to do next; the README's "Common failures" table lists them with the exact text.

10Glossary+
engine
One of the two machines, profiling or serving, each with its own browser page.
contracts
The shared definitions everything agrees on. Pure: no database, no network.
data-transfer
The shared way of copying data: the only opener of the read-only source session, and of the write-scoped publish session.
schema
A named drawer inside a database. Each engine owns its own; every drawer has one writer.
the company database (RDS)
Where the real data lives. Read-only for this system, except the hand-off's one login.
snapshot
A frozen, consistent view of the source for the length of a copy.
staging
The waiting drawer where a fresh copy is checked before it goes live.
vintage / active / previous
A finished, checked copy; the live one; the one before it, kept for rollback.
manifest
The sealed receipt of a copy. Nothing goes live without one.
promotion
The atomic swap that makes a checked copy the live one.
gate
A check a refresh must pass before promotion. A failed blocking gate leaves the live copy untouched; report-only failures are disclosed.
advisory lock
A "do not disturb" sign inside the database: no swap under a reader, no two data operations at once.
lens
The set of questions the AI is asked about a website.
workspace
The person's name plus a selection tag: the label under which a run's answers are stored.
tie salt
A number that breaks ties so the same input gives the same list.
hand-off
Publishing a run's answers back to the company database, on the person's click.
gh
GitHub's command-line tool: signs you in once, clones the private repository, and tells the installer which account you are.
uv
Installs the project's own Python and libraries into a private folder.
